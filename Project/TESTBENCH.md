# Complete Test-Bench Design

The final test bench separates **correctness coverage** from the project's
**Victim Cache performance comparison**. A single conflict-only trace cannot
validate every cache level, so the suite uses four deterministic workloads.

## Workloads

### 1. `repeated`

Repeats one byte address. Expected behavior for every topology containing L1:

- first request: L1 miss
- all remaining requests: L1 hit

This is the simplest proof that L1 lookup, insertion, tag calculation, and hit
accounting work.

### 2. `sequential`

Reads consecutive **words**, not just the first address of consecutive blocks.
The word size and total word count are explicit test-bench parameters. With the
default values:

- block size: 64 bytes
- word size: 4 bytes
- words per block: 16
- sequential requests: 32 words
- generated byte addresses: `0, 4, 8, ..., 124`

The first word of each of the two touched blocks misses in L1. The remaining
15 words in each block hit because the entire 64-byte block was brought into
the cache on the first miss. Therefore every topology containing L1 must
produce exactly **30 L1 hits and 2 L1 misses** with the default configuration.

### 3. `conflict`

Separates addresses by the total L1 capacity. In a direct-mapped L1, all those
addresses map to the same line. This is the project's main performance trace:

- `l1-l2`: repeated accesses should hit in L2 after initial memory misses
- `full`: repeated accesses should often hit in Victim Cache before L2
- the Victim Cache should reduce L2 reads and total cycles

### 4. `mixed`

This workload is a long, deterministic FIFO-versus-LRU stress test. It contains
**1312 requests** by default and has three disjoint regions.

1. **Policy-stress region — 1216 requests**
   - 32 identical epochs are executed.
   - Each epoch first loads nine blocks `A0..A8` into nine different L1 lines.
   - `A0..A3` are then touched repeatedly, so they are the most recently used
     blocks while `A4..A7` remain cold.
   - Nine conflicting blocks `B0..B8`, each exactly one L1 capacity away from
     its corresponding `A` block, evict the `A` blocks into the eight-entry
     Victim Cache and force one replacement.
   - FIFO discards the earliest inserted hot blocks. LRU keeps those hot blocks
     and discards cold blocks instead.
   - Probing `A0..A3` turns the policy decision into measurable Victim hits for
     LRU and L2 hits for FIFO.

2. **Explicit L1-locality region — 32 requests**
   - One address is read 32 times.
   - The first request misses; the remaining 31 requests hit in L1.

3. **Policy-independent Victim-reuse region — 64 requests**
   - Four L1-conflicting blocks are repeated 16 times.
   - This guarantees substantial Victim activity for both FIFO and LRU, while
     the policy-stress region above still makes their performance diverge.

With the default configuration, exact automated expectations are:

| Metric | FIFO | LRU |
|---|---:|---:|
| Requests | 1312 | 1312 |
| L1 hits / misses | 667 / 645 | 667 / 645 |
| Victim hits / misses | 60 / 585 | 188 / 457 |
| L2 hits / misses | 562 / 23 | 434 / 23 |
| Main-memory accesses | 23 | 23 |
| Total cycles | 11922 | 10386 |

Therefore LRU produces **128 more Victim hits**, removes **128 L2 reads**, and
saves **1536 cycles** relative to FIFO. These exact counts and the three policy
comparisons are asserted automatically.

## Architectures

Each workload runs on:

- `memory`
- `l1`
- `l1-l2`
- `full-fifo`
- `full-lru`

## Akita execution of every test case

The test bench does not call the memory hierarchy directly. For every
workload/architecture pair, `testbench.RunCase` creates a fresh `System`, then
constructs and runs a fresh `simadapter.Adapter`. The adapter creates a new
Akita `SerialEngine`, a `MemoryRequestDriver`, a
`MemoryHierarchyExecutor`, their Akita ports, and a `DirectConnection`.

Each request follows this real event-driven path:

```text
driver sends accessRequestMsg
  -> Akita DirectConnection delivers it
  -> hierarchy executor calls System.Access exactly once
  -> executor schedules completeAccessEvent after LatencyCycles
  -> event sends accessResponseMsg
  -> driver validates both Akita correlation ID and project RequestID
  -> driver records the response and issues the next request
```

Only one request is outstanding. This makes all 20 matrix runs deterministic
and preserves the cache-state order, counters, cycle totals, report formatting,
and CSV schema established before the Akita integration. The cache levels are
functional objects inside `System.Access`, not independent Akita components;
Akita is responsible for orchestration, transport, and completion timing.

## Automatic validation

The test bench checks:

- request and response counts
- L1 hit/miss accounting
- Victim hit/miss accounting
- L2 hit/miss/read accounting
- response-location counters
- total cycle accounting
- repeated-address L1 warm-up
- sequential word-by-word address generation
- exact default sequential result: 30 L1 hits and 2 L1 misses
- conflict-trace Victim Cache benefit
- mixed-trace coverage of every level

In addition, `internal/simadapter/adapter_test.go` executes all four workloads
on all five architectures through Akita and compares every response and every
statistics field with the synchronous `System.Run` correctness oracle.

The sequential parameters can be changed independently of the conflict-trace
parameters:

```bash
go run ./cmd/testbench -trace sequential -sequential-words 32 -word-size 4
```

The default command exits non-zero if any check fails:

```bash
go run ./cmd/testbench
```

List all individual checks:

```bash
go run ./cmd/testbench -verbose-checks
```

## CSV output

```bash
go run ./cmd/testbench -csv results.csv
```

The CSV contains per-workload, per-architecture values for cycles, average
cycles per request, all hit/miss counters and rates, Victim swaps, L2 reads and
read/write request counters, and memory accesses.

CSV rows therefore describe simulations that completed through the Akita
engine. No alternate direct-run path is used by `cmd/testbench`.
